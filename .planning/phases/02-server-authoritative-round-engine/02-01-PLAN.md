<objective>
Make the server the sole owner of the game clock, proven end-to-end on the thinnest possible
path: the host starts the game, the room enters WRITING with an absolute deadline, and the
whole round chain then runs to GAME_END on server timers alone with no further client input.

This plan also authors the complete Phase 2 wire contract up front — the expanded `RoomPhase`,
the full snapshot shape, all four new client intents, all new error codes, every Hebrew string,
and every timing constant — so plans 02-02 through 02-05 fill behaviour into a contract that is
already fixed and typechecked, and never have to reopen `shared/protocol.ts`,
`shared/messages.ts`, or `server/src/config.ts`.

Purpose: everything else in this phase, and the whole of Phase 3, hangs off this state machine.
Getting the timer primitive and the snapshot shape right here is what makes the rest additive.

Output: a room that plays a complete (contentless) game of 3 rounds by itself, and a client that
watches it happen.

<assumption_delta_decision>
The deterministic assumption-delta probe fired on this phase with one `chosen` signal:
*"Host can choose how many rounds the game will run"* — a value that was going to be a constant
has become a parameter.

- **Primary noun:** `GameSettings` (`rounds`, `writingSeconds`, `ratingSeconds`).
- **Decision: `promote`.** `GameSettings` becomes a first-class object owned by the `Room`, and it
  is the ONLY thing the round engine reads when it computes a deadline. The numbers in
  `server/src/config.ts` demote from "the value" to "the allowed presets and the seed default" —
  `DEFAULT_WRITING_SECONDS` seeds a new room's settings and is never read again afterwards.
- **Why not add-alongside:** a timer that reads `DEFAULT_WRITING_SECONDS` directly would keep
  working for a default game and silently ignore a host who changed the setting, which is exactly
  the failure the promote/demote rule exists to prevent.
- **Invariant test (accepted):** plan 02-02 asserts that a room whose `settings.writingSeconds`
  was changed schedules its writing deadline from the changed value, not from the default.
</assumption_delta_decision>

    `deadlineAt: number | null = null`.
  - New private state: `phaseTimer: ReturnType<typeof setTimeout> | null = null`.
  - `private schedulePhase(deadlineAt: number, onExpire: () => void): void` — the single timer
    primitive. Clears any existing phase timer first, stores `this.deadlineAt = deadlineAt`, and
    sets one `setTimeout` for `Math.max(0, deadlineAt - Date.now())` whose callback nulls
    `this.phaseTimer`, runs `onExpire`, then calls `this.onStateChanged?.()` — exactly as
    `scheduleFade`'s callback mutates first and notifies second. `Room` must not import `Server`
    and must never call `broadcast` from a timer.
  - `private clearPhaseTimer(): void`, and call it from `dispose()` alongside the existing fade
    and host-transfer teardown.
  - `startGame(playerId: string): StartGameOutcome` where
    `StartGameOutcome = { ok: true } | { ok: false; error: "NOT_HOST" | "WRONG_PHASE" | "NOT_ENOUGH_PLAYERS" }`,
    modelled on `RenameOutcome` — never throws. Refuses unless `playerId === this.hostId` (D-01

    `this.players.size >= MIN_PLAYERS_TO_START` (D-06, unchanged from Phase 1's gate). On success

  - `private enterWriting(): void` — sets `phase = "WRITING"`, clears the round's submissions
    container, and schedules `Date.now() + this.settings.writingSeconds * 1000` (read from
    `this.settings`, never from `DEFAULT_WRITING_SECONDS`) with `closeWriting` as the expiry.
  - `private closeWriting(): void` — in this plan, always goes to `enterRoundEnd()`; plan 02-04
    inserts the rating branch in front of it.
  - `private enterRoundEnd(): void` — sets `phase = "ROUND_END"` and schedules
    `Date.now() + BETWEEN_PHASES_MS` (D-11) with an expiry that either increments `roundIndex`

    `enterGameEnd()`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client socket -> `handlers.ts` | Every `start-game` payload is attacker-controlled; only `socket.data.playerId`, bound at join time by `authMiddleware`, is trusted |
| `handlers.ts` -> `Room` | Handlers may only call typed `Room` methods; they must never assign `room.phase`, `room.deadlineAt` or `room.settings` directly |
| server timer -> room state | Phase advancement has no client input at all; this boundary is the reason LIVE-03 holds |
| `Room` -> per-player snapshot | `snapshotFor(playerId)` is where a player's view is narrowed; anything omitted here can never leak |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Spoofing | `start-game` handler / `Room.startGame` | high | mitigate | `startGame(playerId)` compares `playerId === this.hostId` server-side and returns `NOT_HOST`; the handler passes only `socket.data.playerId`, and the payload carries no identity field a client could forge |
| T-02-09 | Denial of Service | round phase advancement | high | mitigate | No client event advances a phase. Every transition is a `setTimeout` scheduled by `Room.schedulePhase`, and `roundClockInvariants.test.ts` asserts every non-terminal phase holds a non-null `deadlineAt` |
| T-02-10 | Denial of Service | timer surviving room teardown | medium | mitigate | `clearPhaseTimer()` is registered inside `dispose()` alongside the Phase 1 fade/host-transfer teardown; a test advances timers ten writing durations past `dispose()` and asserts no mutation |
| T-02-11 | Tampering | repeated `start-game` from the host | medium | mitigate | `startGame` refuses with `WRONG_PHASE` unless `phase === "LOBBY"`, so a double-tap cannot schedule a second concurrent phase timer |
