### Confirmation Pattern

**Low-stakes actions (skip round, restart game)**: Single confirmation modal with `{action} בטוח?` copy + two buttons (cancel, proceed). No toast or additional confirmation after success — the game state advances on the server's snapshot, same as any other action.

**High-stakes actions (remove player, end game early)**: Single confirmation modal with descriptive copy (include the affected player name or round number for clarity) + two buttons (cancel, proceed). After success, the game state advances immediately from the server's snapshot.

## UI Considerations

### Host Control Placement & Visibility

**In-Game Screens (Round.tsx and its panels during WRITING/RATING/ROUND_END/GAME_END)**:

1. **Where controls surface**: A collapsed/toggleable "Host Controls" panel at the bottom of the screen (below the main panel content) that only mounts if `snapshot.you.isHost === true`.
   
2. **Visual Treatment**: 
   - Use the existing `.settings-panel` CSS class for the container (border, padding, margin already defined)
   - Render a heading "לא עובד? בעזרת המנחה" (Hebrew-only, small/secondary size to signal these are recovery tools, not primary game flow)
   - Four buttons arranged in a 2×2 grid that wraps on narrow phones:
     - "דילוג על הסיבוב" (skip round) — outlined secondary style
     - "הסרת שחקן" (remove player) — outlined secondary style
     - "סיום המשחק" (end game) — outlined secondary style
     - "משחק חדש" (restart) — outlined secondary style

3. **Non-host visibility**: 
   - These controls render to no one except the host (`snapshot.you.isHost === true`)
   - Follow the exact same pattern as Lobby.tsx's `{snapshot.you.isHost && (...)}` gate (line 188+)
   - The controls do not appear, do not reserve space, do not exist in the DOM for non-hosts

4. **Placement in DOM order**: Render after the main panel content (WritingPanel, RatingPanel, etc.) but before the basic roster list (if any) — hosts see their action tools before they see a plain player list.

**Lobby Screen (Lobby.tsx during LOBBY phase)**:

No new host controls needed in the lobby — Phase 2 already added the settings panel and start button. A second row of "break glass" controls would be redundant here; host tools for disruption (skip, remove, end) only make sense once the game has started.

### Confirmation Modal Pattern

**Trigger**: When a host taps "skip round", "end game", or "restart" (the three no-target actions), the client immediately sends the request to the server. Simultaneously, a modal overlay appears with:
- Descriptive message (see copywriting table above)
- Two buttons: "ביטול" (Cancel) or "אישור" (Confirm)

**Flow**:
1. Modal blocks interaction with the main content (fixed overlay with z-index)
2. Cancel: Modal closes, no server action is sent (action is optimistic cancel only)
3. Confirm: Action has already been sent to the server; modal closes once the next snapshot arrives (server's authoritative response)

**"Remove player" is a two-step flow (target selection is not optional — a payload needs `targetPlayerId`)**:
1. Tapping "הסרת שחקן" (remove player) opens a selection list — not a confirmation modal yet. Reuse the existing roster `<ul>` styling (the same list Round.tsx already renders for RATING/REVEAL_BREAK phases), showing every currently-connected player's name as a tappable row. The acting host's own name is excluded from the list (a host cannot remove themselves — restart or end-game cover that case).
2. Tapping a player's name in that list immediately opens the confirmation modal with that name interpolated into the copy ("זה יתנתק את {playerName} מהחדר. בטוח?") — this merges "pick a target" and "confirm" into one two-tap flow rather than a separate select-then-confirm-then-confirm-again sequence.
3. Cancel at the selection-list step or the confirmation step: closes back to the host controls panel, no server action sent.
4. Confirm: sends `CLIENT_EVENTS.hostAction` with `{ targetPlayerId }`, same modal-closes-on-next-snapshot behavior as the other three actions.
5. **Empty-state**: if the host is the only connected player when they tap "remove player" (a real, if rare, state — e.g. everyone else just disconnected), the selection list shows a one-line message ("אין שחקנים אחרים להסרה" — "no other players to remove") instead of an empty `<ul>`, with only a close button, no confirm path.

**Error handling**: If the server rejects the action (e.g., `NOT_HOST` even though the client thought they were host — a sync error), display the error string from `HEBREW_ERRORS` in the modal and offer a "close" button instead of proceeding.

### RTL Audit Checklist (HEB-01)

**Systematic review of every screen** — read aloud in Hebrew word order on a real phone to catch any reversed/incorrect layout:

#### Text & Typography
- [ ] **Text alignment**: All text in `<h1>`, `<p>`, `<li>`, button labels, input placeholders reads left-to-right in Hebrew (browser's RTL auto-adjustment should handle this, but verify visually)
- [ ] **No hardcoded `text-align: left`**: Search codebase for `text-align: left` — none should exist in an RTL doc
- [ ] **No hardcoded `text-align: right`**: Check that no screen has hardcoded `text-align: right` expecting English LTR logic (should default to inheriting RTL from `dir="rtl"`)
- [ ] **`letter-spacing` on Hebrew**: Verify no Hebrew text has CSS `letter-spacing` applied (distorts Hebrew letterforms). Exception: `letter-spacing` only okay on purely-numeric text or embedded English words. Baseline check: `index.css` has no `letter-spacing` — good.
- [ ] **`word-spacing` usage**: Verify where `word-spacing: 0.1em` is used (countdown, round-end-score, best-of-meta, writing-progress) — these are "important numbers" that need visual emphasis without layout distortion.

#### Layout & Directionality
- [ ] **`float: left` or `float: right`**: Search codebase for any float-based layout — none should exist (Flexbox is the standard in this codebase). If any float exists, verify it's intentional (e.g., wrapping text around a floated image, then test on a real phone in RTL).
- [ ] **Absolute positioned elements**: Check `.qr-code`, `.meme-canvas`, `.meme-photo` — they use `margin: 0 auto` (centers regardless of RTL), not `margin-left`/`margin-right` — correct.
- [ ] **Margin and padding**: Verify no CSS uses `margin-left`, `margin-right`, `padding-left`, `padding-right` when logical properties would be safer. Current codebase uses `margin-inline: auto` (line 30 in index.css) and `inset-inline` (line 133) — correct pattern.
- [ ] **Flexbox direction**: Check that `flex-direction: column` is used (not row, which would need RTL flipping). Baseline: WritingPanel, RatingPanel, all panels use `flex-direction: column` — correct.
- [ ] **Grid order**: If any CSS Grid is used, check `grid-auto-flow: row` (not `column`, which reverses in RTL). Current codebase has no Grid — only Flexbox.

## Host Control Implementation Details

### Client-Side Event Emission

Each host action follows the existing pattern from Lobby.tsx's `handleStartGame` / `handleChangeSetting`:

```
socket.once(SERVER_EVENTS.error, onError);
socket.once(SERVER_EVENTS.state, onState);
socket.emit(CLIENT_EVENTS.hostAction, { action: "skip_round" | "remove_player" | "end_game" | "restart_game", ...payload });
```

The four actions defined in `CLIENT_EVENTS`:
- `"skipRound"` payload: `{}` (no parameter; server knows current round)
- `"removePlayer"` payload: `{ targetPlayerId: string }`
- `"endGame"` payload: `{}` (server ends game immediately, computes final scores)
- `"restartGame"` payload: `{}` (server resets scores, returns to LOBBY)

### Server-Side Validation Pattern (Room.ts)

Each action must follow Room.ts's established pattern (see `changeSetting`, `startGame`):

1. **Identity check first**: `if (playerId !== this.hostId) return { ok: false, error: "NOT_HOST" }`
2. **Phase/state validation**: Verify the room is in a phase where the action is allowed
3. **Mutation**: Execute the action (clear round, remove player, end game, reset scores)
4. **Broadcast**: Call `onStateChanged()` to notify all players of the new state

Each returns a typed outcome (e.g., `SkipRoundOutcome`, `RemovePlayerOutcome`).

### Error Code (shared/protocol.ts)

Only reuse `"NOT_HOST"` if a non-host somehow invokes a host action (should never happen, but server validates). No new error codes needed for these actions — they succeed or fail at validation, not at mutation.

## Notes for Executor

1. **Host controls must not leak to non-hosts** — use the `snapshot.you.isHost` check pattern already established in Lobby.tsx (line 188). Do not render these controls to anyone except the host.

2. **Confirmation modals are NOT optimistic** — immediately send the action to the server, then display the confirmation UI while awaiting the response. On error, show the error message and a "close" button. On success, the next snapshot advances the game state.
