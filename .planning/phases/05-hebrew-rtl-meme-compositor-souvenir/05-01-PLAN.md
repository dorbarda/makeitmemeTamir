<objective>
Migrate the wire contract and server-side authority from a plain-text `caption` field plus a
separately-tracked `photoUrl` to a single opaque `meme` field — a base64-encoded PNG the client will
rasterize starting in Plan 05-02 (RESEARCH.md's rasterize-and-transmit decision, the phase's central
architecture change per D-01). This plan does not touch any client rendering surface; it makes
`shared/protocol.ts`, `server/src/rooms/Room.ts`, and `server/src/socket/handlers.ts` internally
consistent on the new shape and migrates every existing test that exercises `submitCaption`/
`ratingStep`/`roundEnd`/`bestOfNight` so the full suite stays green. This is a genuinely atomic
change — every consumer of the old `caption`/`photoUrl` fields must move together, since TypeScript
will not compile a half-migrated state and the wave cannot honestly claim "done" with a red suite —
rather than three independently-shippable pieces spread across plans.

Purpose: every later Phase 5 plan (the canvas compositor, the drag editor, save/share) needs a stable
server contract to write to and read from. Plan 05-02's tracer cannot start until the server accepts
and returns `meme`, so this plan is the foundation the whole rest of the phase depends on.

Output: `shared/protocol.ts`/`Room.ts`/`handlers.ts` speaking `meme` exclusively; the full server test
suite green against the new shape; two new tests (`server/test/fixtures/meme.ts`,
`server/test/memeValidation.test.ts`) proving the new validation branches the threat model requires.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client socket -> `submit-caption` handler | The single point untrusted, client-controlled image data (`meme`) enters server memory |
| `Room.submitCaption` -> `Room.submissions` | Server-authoritative storage; once validated, the exact same bytes are relayed to every other player's device via `ratingStep`/`roundEnd`/`bestOfNight` |
| `Room.submissions` -> every other player's socket | A malformed or oversized payload that slipped past validation would be broadcast to every rater's browser, not just the author's own |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Denial of Service | `Room.submitCaption` size check | high | mitigate | `meme.length > MEME_MAX_BASE64_CHARS` is checked before storage, rejecting an oversized payload with `MEME_TOO_LARGE` before it is ever set into `submissions` or reaches `maybeCollapseWriting`/broadcast — paired with `maxHttpBufferSize` on the Socket.IO transport itself (Task 1) as a second layer above the application-level check |
| T-05-02 | Tampering | `Room.submitCaption` shape check | medium | mitigate | `BASE64_PATTERN.test(meme)` rejects non-base64-shaped content (`CAPTION_REQUIRED`) before storage; downstream `<img src="data:image/png;base64,...">` rendering (Plan 05-02) treats the value as an opaque image src attribute, never `dangerouslySetInnerHTML`, so even a payload that passed shape validation cannot execute as script in a receiving browser |
| T-05-03 | Tampering | `submit-caption` handler identity | low | mitigate | The author is always `data.playerId` from the authenticated socket, exactly like every other mutating handler in this file (`submitRating`, `swapPhoto`) — the payload carries no identity field a client could forge |
