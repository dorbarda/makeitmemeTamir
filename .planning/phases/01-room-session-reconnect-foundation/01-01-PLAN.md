export type PlayerView = {
  id: string;
  name: string;
  connected: boolean;
  isHost: boolean;

  phase: RoomPhase;
  roomCode: string;
  joinUrl: string;      // filled by plan 01-03; "" until then

  canStart: boolean;
  you: { id: string; isHost: boolean };

  | "ROOM_NOT_FOUND"
  | "ROOM_FULL"
  | "NAME_REQUIRED"
  | "NAME_LOCKED"
  | "NOT_IN_ROOM"
  | "RATE_LIMITED";

export const CLIENT_EVENTS = {
  createRoom: "create-room",     // { name: string }

    reconnect on the far end. No manual code entry, no QR, no rename, no capacity message, no
    duplicate-name numbering, no grace delays — those are plans 01-02, 01-03 and 01-04. Everything

    Server, identity layer. `Player.ts` defines `Player` as `{ id: string; token: string; name:
    string; connected: boolean; score: number }` where `id` and `token` are both `crypto.randomUUID()`
    values generated server-side. `score` starts at 0 and exists from day one so that identity
    continuity across a reconnect is provably score-carrying (D-17); no scoring rules are
    implemented here. `SessionRegistry.ts` owns a `Map<token, { roomCode, playerId }>` with
    `issue()`, `bind(token, roomCode, playerId)` and `resolve(token)`. The registry is the only
    place a token becomes an identity — no other module may read `auth.token`.

    Server, room layer. `RoomManager.ts` holds `Map<roomCode, Room>` and exposes `createRoom()` and
    `findRoom(code)`. `createRoom` generates a candidate with nanoid's `customAlphabet('0123456789',
    ROOM_CODE_LENGTH)` (D-01) and retries while the map already holds that code, throwing after 50
    attempts as a defensive bound. `Room.ts` holds `code`, `phase` (defaults to `"LOBBY"`; the
    transition out of it is Phase 2's job, but the field exists now because later plans branch on
    it), `players: Map<playerId, Player>`, `hostId: string | null`, and methods `addPlayer(name)`,
    `attach(playerId)`, `detach(playerId)`, `snapshotFor(playerId): LobbySnapshot` and
    `broadcast(io)`. `snapshotFor` returns the full shape from `shared/protocol.ts` with `joinUrl`
    and `qrDataUrl` as empty strings for now (plan 01-03 fills them), `readyCount` as the count of
    connected players, `canStart` as `players.size >= MIN_PLAYERS_TO_START`, and `isHost` per player
    derived from `hostId`. The first player to occupy an empty room becomes the host and is a full
    entry in `players` like anyone else (D-10) — never a separate non-playing role.

    Server, socket layer. `authMiddleware.ts` exports `createAuthMiddleware(sessions)` for `io.use()`:
    read `socket.handshake.auth?.token`; if `sessions.resolve(token)` returns a binding, put
    `playerId`, `roomCode` and `token` on `socket.data`; otherwise mark `socket.data.isNewSession =
    true` and continue. An unrecognised token must produce a brand-new session, never an error and
    never a match against someone else's record. Never write the token to a log line.

    `handlers.ts` exports `registerHandlers(io, socket, deps)` binding four listeners:
    `create-room` creates a room, adds the sender as its first player and host, issues and binds a
    token, emits `session` to that socket, joins the Socket.IO room channel, then broadcasts the
    snapshot; `join-room` looks the room up (emitting `ROOM_NOT_FOUND` with a Hebrew message if
    absent), adds the player, issues and binds a token, emits `session`, joins the channel,
    broadcasts; `rejoin` reads the binding already placed on `socket.data` by the middleware, finds
    the room, flips that player to `connected: true`, joins the channel, sends that one socket its
    own snapshot immediately and then broadcasts to the room; `request-resync` re-sends the current
    snapshot to the calling socket only. Also handle `disconnect` by flipping the player to
    `connected: false` and broadcasting — the grace-delay refinement is plan 01-04, so for now the
    record is simply retained, never deleted. Wire `createAuthMiddleware` and `registerHandlers`
    into `createServer()` in `app.ts` and expose the real `roomManager` there.

    Client. `sessionStore.ts` exports `SESSION_STORAGE_KEY = "tamir-meme:session"`, `readToken()`,
    `writeToken()` and `clearToken()`, each wrapped so a browser with storage disabled degrades to
    an in-memory value instead of throwing. It stores the token and nothing else — no name, no room
    code, no draft input (D-15). `connection.ts` creates the singleton `socket.io-client` instance
    with `auth: () => ({ token: readToken() ?? undefined })` (the callback form so a token issued
    mid-session is picked up on the next reconnect), `transports: ['websocket']`, and reconnection
    left enabled with Socket.IO's built-in backoff. On the socket's `connect` event it always emits
    `rejoin` — on the very first connect and on every automatic reconnect alike, regardless of
    `socket.recovered`, because connection-state recovery reports false across a genuine
    WiFi-to-LTE change. It persists the token on every `session` event. `gameStore.ts` holds the
    last received `LobbySnapshot` and exposes it to React via `useSyncExternalStore`; it replaces
    the snapshot wholesale on every `state` event and never merges.

    `App.tsx` reads `window.location.pathname`: a path matching `/join/<4 digits>` renders `Join`
    with the code pre-filled from the URL (D-03), anything else renders `Home`. Once the store holds
    a snapshot, `Lobby` renders instead — the screen is a pure function of the snapshot, so a
    returning player lands straight on whatever the room is currently showing with no interstitial
    and no extra tap (D-14). `Home.tsx` is a name field and a create-room button. `Join.tsx` is a
    name field and a join button, with the room code shown read-only from the URL. `Lobby.tsx` lists
    `players` by `id` showing name and connected state, plus the room code. All player-facing text
    on these three screens is Hebrew. Keep styling to the minimum that is legible on a phone; the
    lobby's full presentation is plan 01-03.

    Tests. `server/test/tracer.e2e.test.ts` drives the whole path with real `socket.io-client`
    instances against a real in-process server: client A emits `create-room` and captures its

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| phone browser -> Socket.IO handshake | Untrusted `auth.token` and untrusted intent payloads cross here; the socket is transport, never identity |
| phone browser -> `create-room` / `join-room` | Untrusted display name and room code cross here; unbounded call rate |
| npm registry -> developer machine | Third-party install-time code crosses here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | `authMiddleware.ts` — `auth.token` | high | mitigate | Tokens are `crypto.randomUUID()` issued server-side and resolved only through `SessionRegistry.resolve()`; a token the registry does not hold produces a brand-new session and can never match an existing player. The token is never derived from, or validated against, anything the client supplies. |
| T-01-02 | Elevation of Privilege | `Room.hostId` | high | mitigate | Host is a server-side field on `Room`, set when the first player occupies an empty room and only ever reported outward in the snapshot. No handler reads an `isHost` field from a client payload. |
| T-01-03 | Information Disclosure | logs, URLs | medium | mitigate | The session token is never written to a log line and never appears in a URL or query string — it travels only in the Socket.IO handshake `auth` object. |
| T-01-04 | Spoofing | 4-digit room code | medium | accept | A 10,000-value code space is guessable by an outsider. This is D-01's deliberate UX trade-off for a private, one-night, everyone-in-the-room party, and PROJECT.md's threat model accepts it. Documented, not fixed. Consequence of a guess is a stranger appearing in the roster, which the people in the room will notice immediately. |
| T-01-05 | Denial of Service | `create-room` handler | medium | mitigate | `createRoom()` retries collisions against the live map and throws after 50 attempts rather than looping; the per-socket rate limit on room creation and joining lands in plan 01-02 alongside the capacity cap. |
| T-01-06 | Tampering | in-memory room state | low | accept | A process restart wipes every room. Accepted per PROJECT.md and STACK.md for a single-night event; the operational mitigation ("do not redeploy during the party") is Phase 7's concern. |
| T-01-SC | Tampering | npm installs (`socket.io`, `express`, `nanoid`, `qrcode`, `react`, `vite`, toolchain) | high | mitigate | RESEARCH.md's Package Legitimacy Audit table plus the blocking human checkpoint in Task 1, which must be cleared before the first `npm install` runs. Packages absent from the audit table are treated as `[ASSUMED]` and are enumerated in that checkpoint. |
</threat_model>
