<objective>
Build every way into the room and everything the lobby shows. The primary path is a link pasted
into the WhatsApp group that carries the code, so a joiner sees one screen (D-02, D-03). The QR
code is built and shown as the secondary path (LOBBY-02, D-04), and manual 4-digit entry stays as
the fallback for anyone not in the group (D-04). The lobby then shows the live roster, the ready
count, and the room code kept visible to everyone so any player — not just the host — can re-share
it to a straggler (D-12, LOBBY-05).

Purpose: with roughly twelve people joining at once, crowding around one phone to scan a QR is the
slow path and a link everyone taps is the fast one. This plan makes the fast path the default while
keeping both slower paths working, and makes the lobby the screen the room stares at while waiting.

Output: server-side join-URL and QR generation carried in the snapshot, the home/create screen, the
deep-link and manual-code join screens, the share control, and the full lobby presentation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| phone browser -> `/join/:code` HTTP route | Untrusted path segment reaches the static server before any socket exists |
| phone browser -> `join-room` with a manually typed code | Untrusted 4-digit string used to look up a room |
| request headers -> `resolveOrigin` | Attacker-controllable `Host`/`Origin` headers become part of a URL shown and shared by players |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12 | Spoofing | `resolveOrigin` header derivation | medium | mitigate | `PUBLIC_BASE_URL` takes precedence whenever it is set, and Phase 7 sets it on the deployed host, so the header-derived path is only reachable in local and LAN development. The derived origin is used solely to build a link and a QR, never to make an authorization decision. |
| T-01-13 | Spoofing | 4-digit code brute force through the manual entry screen | medium | accept | Same accepted risk as T-01-04: a 10,000-value space is D-01's deliberate trade-off for a private one-night party. The per-socket join rate guard added in plan 01-02 makes a systematic sweep slow enough to be pointless, and the capacity cap bounds the damage of a lucky guess to one visible stranger in a roster everyone is watching. |
| T-01-14 | Information Disclosure | join URL shared into a WhatsApp group | low | accept | The link is the intended distribution mechanism; anyone holding it can join, which is exactly the product decision (no signup, no password). Forwarding beyond the group is a social risk, not a technical one, and the room is visible to everyone in it. |
| T-01-15 | Tampering | `/join/:code` SPA fallback | low | mitigate | The fallback serves the static shell only and never interpolates the path segment into the returned HTML, so a crafted path cannot inject markup into the served page. |
| T-01-16 | Denial of Service | QR generation on room creation | low | mitigate | The QR data URL is generated exactly once per room and cached on the `Room`, so repeated snapshots cost nothing, and room creation itself is rate-guarded per socket by plan 01-02. |
</threat_model>
