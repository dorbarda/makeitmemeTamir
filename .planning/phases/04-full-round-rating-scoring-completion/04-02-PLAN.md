## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client socket -> Room.swapPhoto | An authenticated player's socket can request a photo swap; the server alone decides the outcome and the new photo. |
| Client socket -> Room.submitRating (existing, Phase 2) | Ratings feed this phase's new scoring math; no new boundary, but the consequence (a persisted score) is new. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-02 | Tampering | Room.swapPhoto | low | mitigate | `SWAP_ALREADY_USED` and `ALREADY_SUBMITTED` guards cap a player to exactly one effective swap per round regardless of how many times `swap-photo` is emitted — repeated emission is a no-op after the first success. |
| T-04-03 | Information Disclosure | Room.snapshotFor (ratingStep/photoAssignments) | medium | mitigate | `yourPhotoFile` only ever exposes the recipient's own assignment; `ratingStep.photoFile` only exposes the meme currently on screen — no snapshot field ever carries another player's not-yet-revealed photo or caption, extending D-14's existing no-leak discipline. |
| T-04-04 | Tampering | Room.applyRoundScoresAndBestOfNight | low | mitigate | Scores are computed exclusively from server-recorded `ratings` (never a client-supplied score value); a client cannot inflate its own or another player's score — inherits Phase 2's `submitRating` refusal set (CANNOT_RATE_OWN, ALREADY_RATED, RATING_OUT_OF_RANGE). |
| T-04-05 | Denial of Service | Room.pickNextPhoto / photoPool.pickPhoto | low | accept | `photoManifest` is fixed at process start from a developer-controlled directory (plan 04-01); no runtime client action can shrink or empty it, so the empty-manifest throw path is unreachable during normal play. |
</threat_model>
